# System architecture

## 1. Purpose

AutoDev converts a trusted work item into a verifiable code-change proposal. It
is an automation controller around coding agents, not a single autonomous
prompt. Reliability comes from assigning probabilistic work to models and
deterministic work to scripts.

The first runtime target is agent-compose. AutoDev uses its projects,
schedulers, webhook events, sandboxes, Git workspaces, Agent runtime, LLM
facade, skills, secrets, sessions, and run lifecycle rather than rebuilding
those facilities.

The exact ownership contract is defined in
[AutoDev and agent-compose responsibility boundary](responsibility-boundary.md).
In particular, webhook authentication, secret storage/injection, sandbox
isolation, and workspace provisioning are platform responsibilities.

## 2. System boundaries

```text
GitHub/GitLab                     agent-compose
-------------                    -------------
Issue webhook -----------------> event source
                                    |
                                    v
                              scheduler trigger
                                    |
                                    v
                          isolated project run/sandbox
                                    |
                                    v
                              AutoDev controller
                              /       |       \
                             /        |        \
                     runtime.agent  scripts   SCM adapter
                     runtime.llm    Git/gates GitHub/GitLab
                             \        |        /
                              \       |       /
                               run state/evidence
```

agent-compose owns runtime infrastructure. AutoDev owns development workflow
semantics. The target repository owns its acceptance policy and validation
commands.

## 3. Execution planes

### 3.1 Agent plane

Use a full coding agent when work needs repository tools and iterative
reasoning:

- repository investigation;
- implementation planning;
- code and test changes;
- semantic review;
- repair from local or CI evidence.

Use the LLM facade for bounded, tool-free transformations:

- task classification;
- failure-log summarization;
- risk labeling;
- report drafting.

Agent output is an untrusted proposal. Important stages require JSON-schema
output and are normalized before entering run state.

### 3.2 Deterministic control plane

Trusted AutoDev controller code owns:

- normalized-event validation and provider payload normalization;
- repository and label allowlists;
- event deduplication and per-repository leases;
- workspace isolation and Git baseline creation;
- branch naming and revision tracking;
- quality-gate materialization and execution;
- command exit codes and evidence capture;
- denied-path and credential checks;
- repair budgets and state transitions;
- commits, push, MR/PR create/update;
- exact-SHA CI lookup and polling;
- issue comments and final status.

agent-compose owns webhook authentication and secret injection. AutoDev must
not duplicate those mechanisms. The current single-sandbox deployment removes
SCM variables before child Agent calls, but strict non-access requires a future
agent-compose-enforced publisher capability or separate privileged sandbox.

## 4. Main components

### 4.1 Event adapter

Normalizes GitHub and GitLab payloads into a provider-neutral `WorkItem`.
Provider headers and payloads remain boundary types and are never used directly
by workflow policy.

```ts
interface WorkItem {
  provider: "github" | "gitlab";
  deliveryId: string;
  action: string;
  repository: RepositoryRef;
  issue: IssueRef;
  revision: string;
}
```

### 4.2 Admission policy

Default admission requires all of the following:

- repository is allowlisted;
- event is an actionable issue transition;
- required label such as `ai-ready` is present;
- issue-author, event-actor, and repository trust policy passes;
- no conflicting active run owns the repository lease;
- the event is not generated by AutoDev itself.

Policy may select `plan-only`, `draft`, `no-push`, `full-verify`, or
`human-required` modes.

### 4.3 Workspace manager

Every mutating run needs an isolated workspace. The preferred model is one
sandbox/worktree per run. A sticky shared workspace is permitted only with an
exclusive repository lease. State records the base branch, base SHA, task
branch, head SHA, and dirty status at every checkpoint.

### 4.4 Workflow reconciler

Stages are conditions over durable state, not a chain of blind function calls.
On restart the controller reads state, observes Git/SCM/CI reality, and executes
only the next unsatisfied condition.

```text
accepted -> workspace_ready -> planned -> gates_frozen -> implemented
         -> locally_verified -> reviewed -> published -> ci_green -> completed
```

Repair invalidates downstream conditions by revision:

```text
implementation revision N
  -> verification for revision N
  -> publication for revision N
  -> CI for pushed SHA of revision N
```

This prevents a successful result for an older revision from satisfying a
newer run state.

### 4.5 Policy and quality gates

Gates come from four ordered sources:

1. global safety defaults;
2. repository policy checked into the AutoDev project;
3. task-declared acceptance criteria;
4. plan signals and changed-path fallback rules.

The controller materializes gates after planning and freezes their IDs and
definitions. The implementation agent cannot weaken them. Actual changed paths
may add conservative fallback gates but cannot remove frozen gates.

Gate types include:

- command;
- Git invariant;
- changed-path policy;
- structured evidence;
- human approval;
- SCM/CI invariant.

### 4.6 Runtime adapter

`src/runtime` is a thin adapter over agent-compose runtime APIs. It provides
stage-oriented invocation, schema validation, timeout/cancellation, transcript
references, and normalized usage metadata without reimplementing provider
runners.

The adapter must preserve provider-neutral workflow semantics. Codex, Claude,
Gemini, OpenCode, or Pi may be selected by configuration when their capabilities
satisfy the stage.

### 4.7 SCM adapter

The workflow depends on a provider-neutral interface for issue comments,
change requests, pipelines, and job logs. GitHub and GitLab implementations own
pagination, authentication, rate limits, error mapping, and idempotent lookup.

Publishing always follows observe-before-create:

1. inspect remote task branch;
2. push expected local SHA with safe force policy disabled by default;
3. find an existing MR/PR by source branch and issue identity;
4. create or update idempotently;
5. persist remote IDs and pushed SHA.

### 4.8 State and evidence

Durable state records decisions; artifacts store potentially large evidence.

State contains:

- normalized task identity;
- stage and revision status;
- lease and idempotency keys;
- Git baseline/checkpoints;
- frozen gates and outcomes;
- repair counters;
- MR/PR identity and pushed SHA;
- CI pipeline identity and terminal status;
- sanitized error and final summary.

Artifacts contain:

- hydrated issue body and safe attachments;
- agent transcripts by reference;
- command stdout/stderr;
- diffs and review reports;
- CI failure logs;
- screenshots and other required evidence.

## 5. Workflow

### Intake

Authenticate, normalize, deduplicate, authorize, and acquire a lease. Rejected
events produce an auditable reason without starting a coding agent.

### Probe and plan

Inspect repository guidance and build metadata. The planning agent returns
acceptance criteria, affected areas, implementation steps, risk signals,
expected paths, proposed checks, human questions, and MR/PR intent.

Ambiguity with material product or security impact stops for human input.

### Implement and verify

The implementation agent edits only the local task branch. Trusted scripts
compute the diff and run frozen gates. A semantic reviewer assesses requirement
coverage but cannot turn a failed mechanical gate into a pass.

### Repair

Repair receives bounded evidence, not entire unrestricted logs. Each repair
creates a new implementation revision and invalidates verify/publish/CI results.
Local and CI repair have separate finite budgets.

### Publish and CI

Only after the final gate passes does trusted code commit/push and create or
update a draft MR/PR. CI observation is bound to the pushed SHA. Failure logs
may trigger CI repair; success completes the run. Auto-merge is out of scope by
default.

## 6. Concurrency and recovery

- One mutating lease per repository is the safe MVP default.
- A later implementation may allow per-run worktrees and parallel issues.
- Every external operation has an idempotency key or observe-before-act rule.
- A restarted controller reconciles state with Git and SCM rather than trusting
  the last local write.
- Cancellation propagates to agents, commands, and polling loops.
- Time and attempt budgets are persisted, not held only in memory.

## 7. Security model

Issue text, comments, repository content, patches, attachments, command output,
and CI logs are untrusted input and may contain prompt injection.

Mandatory controls:

- repository and event allowlists;
- webhook signature/token validation;
- secret isolation from agent prompts and transcripts;
- least-privilege SCM tokens;
- network and filesystem sandboxing;
- denied/high-risk path policies;
- deterministic push and MR/PR authorization;
- no automatic merge or deployment;
- sanitized logs and bounded artifacts;
- human approval for policy-selected changes.

## 8. Portability

Porting AutoDev to a repository should require only:

- a Git workspace URL and default ref;
- SCM provider and credentials;
- webhook source registration;
- repository policy and validation commands;
- optional repository-specific skills;
- model/provider selection.

Workflow source should not be forked for normal project adoption.
